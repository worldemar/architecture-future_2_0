# Обоснование конфигурации инфраструктуры (Task 4)

## 1. Выбор ресурсов и параметров

### Вычислительные ресурсы (VM)
Мы используем виртуальные машины (Yandex Compute Cloud) для развертывания компонентов "Витрины данных".

- **App Server (`app-server-1`):**
  - **Роль:** Хостинг BI-инструмента (например, Apache Superset) и веб-интерфейса портала самообслуживания.
  - **Размер:** 2 vCPU, 4 GB RAM. Это минимально достаточная конфигурация для запуска BI-приложения средней нагрузки. Легко масштабируется вертикально или горизонтально (через Instance Groups) при росте числа пользователей.
  - **Сеть:** Имеет публичный IP (`nat = true`) для доступа пользователей из интернета (или через VPN, если доступ ограничен корпоративной сетью, но для демонстрации включен NAT).

- **DB Server (`db-server-1`):**
  - **Роль:** Хостинг аналитической базы данных (ClickHouse).
  - **Размер:** 4 vCPU, 8 GB RAM. Аналитические запросы требуют больше памяти и CPU для агрегации данных.
  - **Сеть:** Только внутренний IP (`nat = false`). Доступ к БД разрешен только с App Server или через бастион-хост (безопасность). Прямой доступ из интернета закрыт.

### Хранение данных (Disks)
- **Boot Disks:** Стандартные диски (20-30 ГБ) для ОС и бинарных файлов приложений.
- **Data Disk (`db-data-disk`):** Отдельный диск 100 ГБ типа `network-hdd`.
   - **Причина:** Отделение данных от ОС позволяет легко делать снапшоты данных, изменять размер диска без пересоздания VM и обеспечивает сохранность данных при пересоздании инстанса БД. `network-hdd` выбран как экономичный вариант для больших объемов данных.

### Сеть (VPC)
- Используется одна сеть `future-network` и одна подсеть `future-subnet-a`.
- Это упрощает маршрутизацию на старте. В будущем можно добавить подсети в других зонах доступности (ru-central1-b, c) для отказоустойчивости.

## 2. Декларативный подход и IaC

### Почему Terraform?
Использование Terraform (Infrastructure as Code) вместо ручного создания ресурсов в консоли дает следующие преимущества:

1. **Воспроизводимость:** Вся инфраструктура описана в коде. Мы можем поднять точно такую же среду (например, `staging` или `dev`) за считанные минуты, просто изменив переменные.
2. **Версионирование:** Файлы конфигурации хранятся в Git. Мы видим историю изменений: кто, когда и зачем изменил размер диска или открыл порт. Можно откатить изменения (`git revert`).
3. **Масштабируемость:** Добавление новых серверов - это просто изменение цифры в параметре `count` или добавление блока ресурса, а не часы кликанья в интерфейсе.
4. **Уменьшение человеческого фактора:** Исключаются ошибки ручной настройки (например, "забыл привязать диск" или "выбрал не ту подсеть").
5. **Документация:** Код `main.tf` сам по себе является актуальной документацией инфраструктуры.

### Разделение ответственности
- **Terraform (Infrastructure as Code):** Управляет "железом" и сетью. Это VM, диски, VPC, подсети, статические IP.
- **Ручные операции / Configuration Management:**
    - **Prerequisites:** Создание облачного аккаунта, сервисного аккаунта для Terraform и генерация SSH-ключей производится вручную один раз.
    - **Software Provisioning:** В текущей конфигурации Terraform разворачивает "чистые" виртуальные машины с Ubuntu. Установка и настройка ПО (ClickHouse, BI-система) предполагается как следующий этап (вручную или через Ansible), что отражено на диаграмме. Это позволяет разделить управление инфраструктурой (редко меняется) и конфигурацией приложений (часто меняется).

### Декларативный подход

Мы описываем *желаемое состояние* системы ("хочу 2 сервера и 1 сеть"), а не набор команд ("создай сеть", "создай сервер"). Terraform сам вычисляет разницу между текущим состоянием облака и желаемым, и выполняет только необходимые действия. Это делает управление инфраструктурой предсказуемым и безопасным.
