# Задание 3. Разработка технологического радара и роадмапа изменений

## 1. Технологический радар

Технологический радар визуализирует текущий и целевой ландшафт технологий компании «Будущее 2.0». Он помогает командам выбирать правильные инструменты и понимать стратегическое направление развития.

### Кольца радара:
- **ADOPT (Принимать):** Технологии, в которых мы уверены. Стандарт для использования в продакшене.
- **TRIAL (Пробовать):** Технологии, которые мы успешно попробовали в пилотных проектах. Рекомендуются для новых сервисов, чтобы подтвердить их эффективность.
- **ASSESS (Оценивать):** Перспективные технологии, которые стоит изучить и протестировать.
- **HOLD (Остановить):** Технологии, которые не рекомендуются для новых проектов. Используются только для поддержки легаси.

### Детальное описание секторов

#### 1. Данные и Аналитика
| Технология | Кольцо | Обоснование и Бизнес-сценарии |
| :--- | :--- | :--- |
| **ClickHouse** | **TRIAL** | **Цель:** Быстрая аналитическая отчетность. <br> **Сценарий:** Построение витрин данных для портала самообслуживания. Обеспечивает мгновенный отклик на больших объемах данных (сотни ТБ). |
| **Apache Kafka** | **TRIAL** | **Цель:** Интеграция в реальном времени. <br> **Сценарий:** Обмен событиями между Финтехом, ИИ и Медициной. Отвязка от DWH как средства интеграции. |
| **S3 (Object Storage)** | **TRIAL** | **Цель:** Дешевое хранение сырых данных (Data Lake). <br> **Сценарий:** Хранение архивов, логов, неструктурированных данных для ИИ. |
| **dbt** | **TRIAL** | **Цель:** Управление трансформациями данных (T в ELT). <br> **Сценарий:** Прозрачная логика подготовки витрин, версионирование бизнес-логики данных. |
| **Apache Superset** | **TRIAL** | **Цель:** Портал самообслуживания (BI). <br> **Сценарий:** Замена Power BI для широкого круга пользователей. Экономия на лицензиях, гибкость. |
| **Debezium** | **TRIAL** | **Цель:** CDC (Change Data Capture). <br> **Сценарий:** Репликация данных из Legacy SQL Server в Data Lake без нагрузки на источник. |
| **MS SQL Server 2008** | **HOLD** | **Причина:** Устаревшая версия, сложность масштабирования, единая точка отказа. Поддержка только существующих процессов до миграции. |
| **Power BI** | **HOLD** | **Причина:** Высокая стоимость масштабирования, зависимость от экосистемы MS. Постепенная замена на Open Source решения. |

## 2. Роадмап изменений

План трансформации рассчитан на 1 год и разбит на 4 квартала.

### Этап 1: Фундамент и MVP Витрины (Месяцы 1-3)
**Цель:** Подготовить облачную инфраструктуру и дать бизнесу первый доступ к быстрой отчетности.

| Задача | Результат | Ответственные | Ресурсы |
| :--- | :--- | :--- | :--- |
| **Развертывание Cloud Foundation** | Настроена сеть, безопасность, K8s кластер в Yandex Cloud. Описано в Terraform. Настроен мониторинг (Prometheus). | DevOps Team | Бюджет на облако, 2 DevOps инженера |
| **Data Lakehouse Setup** | Развернуты S3 и ClickHouse. Настроен CDC (Debezium) из SQL Server для критичных таблиц. | Data Platform Team | Сервера ClickHouse, Kafka |
| **MVP Портала самообслуживания** | Запущен Apache Superset с 5-10 ключевыми дашбордами (Финансы, Клиенты). | BI Team | Аналитики, BI-разработчик |

**Обоснование для бизнеса:**
- Снижение рисков: подготовка надежной площадки для миграции.
- Быстрые победы: руководство получает доступ к быстрым отчетам уже через 3 месяца, не дожидаясь полной переделки системы.

### Этап 2: Разделение доменов и Новые сервисы (Месяцы 4-6)
**Цель:** Обеспечить независимое развитие Финтеха и ИИ.

| Задача | Результат | Ответственные | Ресурсы |
| :--- | :--- | :--- | :--- |
| **Миграция Финтех-сервисов** | Финтех-сервисы перенесены в K8s. База данных отделена от DWH (свой PostgreSQL). Обмен данными через Kafka. | Fintech Team | Backend Devs, QA |
| **Внедрение SSO (Keycloak)** | Единая авторизация для всех новых сервисов и портала. | Security / Platform | Security Specialist |
| **Интеграция ИИ-сервисов** | ИИ получает данные из Data Lake (S3) вместо прямой нагрузки на DWH. | AI Team | Data Engineers |

**Обоснование для бизнеса:**
- Time-to-Market: Финтех команда может релизить фичи независимо от релизных циклов монолита.
- Безопасность: Централизованное управление доступами через SSO.

### Этап 3: Масштабирование и Отказ от Legacy (Месяцы 7-9)
**Цель:** Снижение технического долга и масштабирование витрины.

| Задача | Результат | Ответственные | Ресурсы |
| :--- | :--- | :--- | :--- |
| **Расширение Витрины данных** | Подключение всех доменов к Superset. Обучение пользователей Self-Service инструментам. | BI Team / Data Team | Обучающие материалы, тренеры |
| **Strangler Fig для PowerBuilder** | Замена ключевых интерфейсов операторов на Web UI (React). | Frontend Team | Frontend Devs, UX/UI |
| **Оптимизация DWH** | Вывод из эксплуатации неиспользуемых процедур в SQL Server. Снижение нагрузки на легаси. | DBA / Legacy Team | DBA |

**Обоснование для бизнеса:**
- Эффективность сотрудников: Новый Web UI ускоряет работу операторов.
- Демократизация данных: Бизнес-пользователи сами строят отчеты, снижая нагрузку на IT.

### Этап 4: Финализация и Data Mesh (Месяцы 10-12)
**Цель:** Переход к децентрализованному управлению данными.

| Задача | Результат | Ответственные | Ресурсы |
| :--- | :--- | :--- | :--- |
| **Внедрение практик Data Mesh** | Продуктовые команды сами публикуют "Data Products" в Data Lake. | All Teams | Data Governance Officer |
| **Полная изоляция Legacy** | SQL Server 2008 остается только как архив или бэкенд для остаточных процессов. Вся аналитика в облаке. | Architecture Team | - |
| **Подключение Партнеров** | API Gateway настроен для безопасной интеграции с Фармой и Электроникой. | Platform Team | Integration Architects |

**Обоснование для бизнеса:**
- Масштабируемость бизнеса: Готовность к подключению любых новых партнеров через стандартные API.
- Снижение TCO: Минимизация затрат на поддержку старого оборудования и лицензий.
