# Дополнительные предположения и архитектурные решения

## 1. Технологический стек и инфраструктура
*Поскольку в задании не указан конкретный облачный провайдер и детальный стек, принимаем следующие решения:*

- **Облачный провайдер:** **Yandex Cloud**. Выбран для соответствия требованиям 152-ФЗ (хранение данных в РФ) и минимизации сетевых задержек.
- **Архитектура данных (Data Platform):**
    - Используем паттерн **Data Lakehouse**:
        - **S3 (Object Storage):** Для дешевого хранения "сырых" данных и архивов (сотни терабайт).
        - **ClickHouse:** В качестве движка для "Витрины данных" (обеспечивает требование "быстрой отчетности" на больших объемах).
    - **Инструмент Витрины ("Data Showcase"):** 
        - Основные потребители: **Головной офис** (управленческая отчетность) и аналитики в доменах.
        - Предполагаем использование Open Source BI-инструмента (например, **Apache Superset** или **Metabase**) поверх ClickHouse для реализации "портала самообслуживания".
        - **Семантический слой:** Реализуется на уровне dbt (data build tool) или внутри BI-инструмента, предоставляя пользователям понятные бизнес-термины вместо технических имен полей, что критично для Self-Service.
    - **Интеграция (ETL/ELT):** 
        - **CDC (Change Data Capture):** (например, Debezium/Kafka Connect) для репликации данных из Legacy SQL Server.
        - **Event Streaming:** Внедрение **Apache Kafka** как центральной нервной системы для обмена событиями между микросервисами (Финтех, ИИ) и наполнения Data Lake. Это позволит развязать сервисы и уйти от интеграции через БД.
        - **Legacy Integration:** Apache Camel остается для поддержки старых интеграций до момента их полного вывода из эксплуатации, но новые потоки строятся на Kafka/gRPC.
        - **Фильтрация данных:** 
            - **Включены в витрину:** Финансы, Счета, Кредиты, Персонал, Инвентаризация, Клиенты (обезличенные или с ограниченным доступом).
            - **Исключены из витрины:** Медицинские карты, истории болезней, результаты исследований (строгий запрет согласно заданию).

- **Вычислительная платформа:**
    - Основные приложения (микросервисы Финтеха, ИИ, новые адаптеры) будут работать в **Kubernetes**.
    - *Разрешение противоречия в задании:* Для Task 4 (где требуется IaaS/Terraform для VM/Disk/Network) мы моделируем сценарий развертывания **Self-hosted Kubernetes** (или его узлов) на базе виртуальных машин. Это позволяет выполнить требование задания по работе с IaaS уровнем, хотя в реальном продакшене часто предпочтительнее Managed K8s.

## 2. Границы и интеграция доменов
*Уточняем характер взаимодействия с новыми направлениями:*

- **Партнеры (Фарма, Электроника):** Считаем их **внешними доменами**. Интеграция только через публичный API Gateway. Прямой доступ к внутренним БД запрещен.
- **Изоляция медицинских данных:** 
    - Данные разделены на уровне **сетевых сегментов (VPC)** и **схем хранения**.
    - Медицинский домен (Medical Core) физически изолирован от Аналитического домена (Data Showcase).
    - Соблюдение **PCI DSS** для финтех-сегмента и **152-ФЗ** (или аналогов) для медицинского контура.

## 3. Организационные и процессные допущения
- **Команды:** Переход к кросс-функциональным продуктовым командам (Stream-aligned teams) для каждого домена (Финтех, Медицина, Платформа данных). Это необходимо для выполнения требования о "независимом развитии направлений".
- **Пользователи:** Рассчитываем на нагрузку от ~1000-5000 внутренних пользователей.
- **Аутентификация:** Внедрение единого **SSO (Keycloak)** для сквозного доступа сотрудников клиник и банка к порталу.
- **Миграция (Legacy):** Используем стратегию **Strangler Fig** ("Удушение монолита").
    - Текущий SQL Server 2008 остается "Source of Truth" на первое время, но новые фичи пишутся сбоку.
    - PowerBuilder интерфейсы постепенно заменяются на веб-приложения, но на старте поддерживаются.
- **CI/CD и Observability:**
    - Предполагаем наличие централизованной системы логирования (ELK/Loki) и мониторинга (Prometheus/Grafana) в целевой архитектуре.
    - Пайплайны развертывания (GitLab CI/GitHub Actions) управляют накатом инфраструктуры (Terraform) и приложений (Helm).

## 4. Допущения для Task 4 (Terraform)
- В рамках задания мы описываем инфраструктуру для одного из сегментов (например, вычислительный кластер для аналитики или базовую сетевую инфраструктуру).
- Используем **S3** для хранения стейта Terraform (remote state) для обеспечения командной работы, даже если в рамках сдачи это будет локальный файл.

## 5. Нефункциональные требования (NFR)
- **Доступность (Availability):** 
    - Critical Path (Прием пациентов, Платежи): 99.95%.
    - Analytics/Reporting: 99.5% (допустимы краткосрочные простои).
- **Масштабируемость:**
    - Архитектура должна поддерживать горизонтальное масштабирование (Auto-scaling) для вычислительных узлов при пиковых нагрузках (закрытие отчетного периода).
- **Безопасность:**
    - Реализация принципа **Zero Trust** во внутренней сети.
    - Шифрование данных в покое (At Rest) и при передаче (In Transit).
